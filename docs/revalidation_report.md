## `comm_dep` Sidecar Analysis

### Role And Schema

The solver-side `comm_dep.csv` has four integer columns with no header:

```text
src_rank,src_label_offset,dst_rank,dst_label_offset
```

`solver/file_parser.py::CommDepFileParser` reads these rows. `solver/dep_graph_generator.py` then adds cross-rank send-to-receive edges from each row. This sidecar is needed because repeated tags and trace-specific matching behavior cannot always be reconstructed safely from a GOAL file by looking only at `(src,dst,tag,cpu)`.

The sidecar is separate from the NCCL metadata sidecars written by `tools/nccl_generator`, such as `collective_instances.csv`, `goal_label_ranges.csv`, `comm_info.csv`, and `comm_ring_info.csv`.

For V2 generator inputs, the answer to "can we regenerate it?" is yes for the intended pipeline: start from NSYS-exported SQLite, run the V2 NCCL generator to obtain one GOAL rank per GPU plus metadata sidecars, then run patched LogGOPSim with `--comm-dep-out` to emit the LP sidecar. The remaining blocked cases are blocked because the local artifact has only a public prebuilt GOAL without matching raw V2 SQLite/metadata, because the public GOAL's tags do not carry enough reliable ordering information for the GOAL-only fallback, or because the exact paper workload's raw inputs have not been located.
